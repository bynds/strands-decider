# The decider on Jibo

A native runtime for Strands Decider on the original Jibo robot (32-bit ARMv7, Tegra K1, glibc
2.21), and the tools that check it against the Python engine. The design, the budget and the plan
are in [docs/jibo-port.md](../../docs/jibo-port.md); this file says what exists, how to build and
run it, and what has been measured. Paths are relative to this directory unless they are links.

## What is here

| Path | What it is |
| --- | --- |
| `runtime/` | C99, no dependency beyond libc and libm (and libdl for the GL backend). `jd_unicode.c` (UTF-8, the regex classes, NFC), `jd_tokenizer.c` (Qwen's pre-tokenizer and byte-level BPE), `jd_model.c` (the Qwen3.5 forward: Gated DeltaNet, gated attention with partial RoPE, SwiGLU), `jd_kernels.c` (matmul over f32, q8, q4 weights, NEON on ARM), `jd_engine.c` (prompting.py's rendering, infer.py's `_fit` and shared prefix, the pointer head, the answers), `jd_json.c` (the request reader, and Python's `json.dumps(indent=2, ensure_ascii=False)` for structured content), `jd_gl.c` (the GL compute backend: so far the matmul), `main.c` (`jibo-decider ask`) |
| `runtime/unicode_tables.h` | generated by `tools/gen_unicode_tables.py` |
| `tools/export_jdw.py` | a checkpoint to `model.jdw`, `tokenizer.jdt` and `manifest.json` (`jdw.py`, `jdt.py` hold the formats) |
| `tools/jibo-gl-probe.c` | the first GPU deliverable: a GL 4.3 compute context of its own, the limits, a checked dispatch, timings |
| `tools/bench_op.c` | one matrix of a real model on the CPU and on the GPU, timed and compared |
| `tools/jevbench_serve.py` | stands in for `strands-decider serve` so `evaluation/jevbench/jevbench.sh` scores the C runtime |
| `client/decider-client.js` | a skill's client for `jibo-decider serve`: ES5, callbacks, the built-in `net` module only |
| `scripts/robot-run.sh` | the robot-side steps (deploy, probe, bench, ask, status, cleanup), for the owner to run within the agreed scope |
| `tests/` | parity against the Python engine: tokens (`tokenizer_parity.py`), every layer (`forward_parity.py`), whole responses (`engine_parity.py`); `tok_dump.c` and `fwd_dump.c` are their C helpers |
| `scripts/build-jibo.sh`, `scripts/check-jibo-abi.sh` | the cross-build and the check that the result loads on the robot |

[../../tests/test_jibo_runtime.py](../../tests/test_jibo_runtime.py) runs the parity checks in CI
on a tiny random Qwen3.5, with the host compiler, or cross-compiled under an emulator (its
docstring has the command).

## Build

```bash
make OUT=build                     # this machine: jibo-decider, the test helpers, bench-op, the probe
make OUT=build CFLAGS="-O3 -march=native -fopenmp"   # faster parity runs on x86 (the robot build is single-threaded)
```

For the robot, `scripts/build-jibo.sh OUT_DIR` cross-builds and then refuses anything
`scripts/check-jibo-abi.sh` would not load on Jibo (ELF32 ARM, hard float, the armhf loader,
only libc/libm/libdl/libpthread, nothing above `GLIBC_2.21`, no libstdc++):

```bash
JIBO_CC=/path/to/jibo-armcc-wrapper scripts/build-jibo.sh out/   # the owner's toolchain (Linaro GCC 4.8.4)
JIBO_SYSROOT=/path/to/sysroot scripts/build-jibo.sh out/         # stand-in: arm-linux-gnueabihf-gcc + a glibc <= 2.21 sysroot
```

The stand-in sysroot used so far is Debian 8's glibc 2.19 (`libc6`, `libc6-dev` 2.19-18+deb8u10
and `linux-libc-dev` 3.16.56-1+deb8u1, armhf, from archive.debian.org), extracted with
`dpkg-deb -x` and with its absolute symlinks pointed inside the sysroot. The binaries it gives
need at most `GLIBC_2.17`.

## Export a checkpoint

```bash
python tools/export_jdw.py StrandsAgents/strands-decider-2B-hobson-v21 out/v21-q4 --weights q4
```

`--weights f32` is for parity tests, `q8` and `q4` for the robot. The LoRA adapter is merged in
fp32 before rounding. The 4-bit scales are chosen per block of 32 to minimise squared error. The
embedding table is stored bf16 (exact: it is not adapted) and only ever read row by row from the
memory-mapped file. The tokenizer pipeline is taken from the tokenizer as transformers loads it,
which matters: `Qwen2Tokenizer` replaces the split regex that Qwen3.5's own tokenizer.json
declares, and the exporter records which one it wrote.

## Ask a question

```bash
echo '{"state": "Help! My payouts have been failing for 3 days!",
       "questions": {"is_urgent": {"type": "noul", "instructions": "Does this convey urgency?"}}}' |
  build/jibo-decider ask out/v21-q4/model.jdw out/v21-q4/tokenizer.jdt
```

The request and the response are those of `POST /v1/systemone`. `jibo-decider serve ... --socket
PATH` answers the same requests on a Unix socket (mode 0660), one per connection: write the
request, shut down the write side, read the response. `{"health": true}` describes the model.
`--max-temp C --thermal FILE` and `--min-avail-mb N` make it refuse work, with a `busy` detail,
while a thermal zone is too hot or memory too low. `--window N` sets the context
window (the checkpoint's own by default; the robot's default is to be 512), `--strict-window`,
`--no-prefix-cache` and `--raw` (unrounded probabilities) mirror the Python engine. A structured
(JSON) state, instruction or option description is rendered as Python's
`json.dumps(indent=2, ensure_ascii=False)` writes it: key order kept, a repeated key in its first
place with its last value, Python's float `repr`, integers as written. The one thing refused is
`\u0000` inside a string. `jibo-decider render < request.json` prints the rendered prompt pieces.

## Check it against the Python engine

```bash
python tests/tokenizer_parity.py build/tok_dump out/v21-f32/tokenizer.jdt StrandsAgents/strands-decider-2B-hobson-v21
python tests/forward_parity.py build/fwd_dump out/v21-f32/model.jdw StrandsAgents/strands-decider-2B-hobson-v21 --split 50
python tests/engine_parity.py build/jibo-decider out/v21-f32/model.jdw out/v21-f32/tokenizer.jdt StrandsAgents/strands-decider-2B-hobson-v21
```

## On the robot

Nothing in this directory has run on a Jibo. Running anything there, even from `/tmp`, is a
deployment step inside the owner's agreed scope (docs/jibo-port.md, Coexistence and safety rules).
The first runs, in order, once the scope is agreed:

1. `jibo-gl-probe` as `jibo-skill`, under the same display access and library shim as the game
   host's `run.sh`. It prints JSON lines; keep them in `results/`.
2. `bench-op model.jdw l0.up --tokens 128` with a q4 export of the 0.8B decider, then the
   `--rows-per-dispatch` and `--tt` sweeps, while the eye animates.
3. `jibo-decider ask` on the CPU, with `/usr/bin/time -v` for the resident set.

## Measured so far

All on x86 (this is not the robot), against v21:

- **Tokenizer:** identical ids and byte offsets to Hugging Face on 5,431 texts, 2.7 million
  tokens: every prompt of the evaluation files (300 per file) and 3,000 adversarial strings
  (combining marks, Hangul, emoji, mixed whitespace, added-token strings). Both split variants.
  NFC agrees with Python's on all of them.
- **Forward, fp32:** every layer within 3e-6 of torch (largest difference relative to the
  largest activation), on a 127-token prompt, in one pass and continued from a copied state.
- **Whole responses, fp32 (parity stage 1):** on evaluation/device_parity.py's 18 requests
  (54 answers, states of about 40 to 3,000 tokens, one question and five), no answer changes,
  token counts are identical, every rounded response is byte-identical to the Python engine's,
  and the largest probability difference is 4.9e-5, inside the engine's 4-decimal rounding.
- **Quantisation, v21 (2B), the same 54 answers against the Python engine in fp32:**

  | weights | answers changed | largest probability difference | median |
  | --- | --- | --- | --- |
  | f32 | 0 | 0.00005 (rounding) | |
  | q8 | 0 | 0.0084 | |
  | q4, rounded to nearest | 2 (both near coin flips: 0.55 and 0.52 in the reference) | 0.150 | 0.019 |

  q8 passes parity stage 2 but does not fit the memory ceiling (below); plain q4 fits but loses
  calibration, which is why the exporter has GPTQ (`--gptq N`) and per-type 8-bit overrides
  (`--q8 down`).
- **Memory, 0.8B at q4 (a stand-in decider on Qwen3.5-0.8B-Base: right shapes, meaningless
  answers):** 333 MB peak resident set for a three-question request with a 512-token window, on
  x86. At q8 it is 562 MB, over the 400 MB ceiling, so q4 is the format. The file is 795 MB, of
  which 508 MB is the bf16 embedding table, read a row at a time.
- **Speed, CPU, same stand-in:** 17 s on one 2.1 GHz Xeon core for 226 tokens (three
  questions). The A15 will be slower; the CPU path is the reference and the fallback, and the
  2-second target rests on the GPU.
- **Emulated ARMv7** (qemu, NEON kernels): the tiny-model parity tests pass.
- **GL matmul:** matches the CPU kernel to 2e-6 relative on Mesa llvmpipe.
